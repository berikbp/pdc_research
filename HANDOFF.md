## 1. Проект
- Курс Parallel and Distributed Computing, открытый проект без формальных требований. Команда, включая Берика (автор инфраструктуры).
- Исходная тема (proposal): memory-constrained CPU–GPU инференс LLM для английского и казахского. RQ1: меняет ли язык лучшую конфигурацию CPU–GPU при равной длине в токенах. RQ2: улучшает ли политика, учитывающая длину и язык, выбор конфигурации.
- Прежний стенд: ноутбук Берика, RTX 4060 8 ГБ, 8 ядер, Windows + WSL (около 11 ГБ RAM видно), llama.cpp (llama-server), Qwen2.5-7B Q4_K_M (около 4,7 ГБ).

## 3. Вывод анализа
Исходный RQ1 плохой: (1) при равной длине язык влиять не может, разница 0,05–0,1%; (2) нехватки памяти не было, полный offload всегда выигрывает; (3) фиксированные 64 выходных токена убили эффект: казахский дал в 3,2 раза больше входных токенов (298,8 против 92,8), latency выросла лишь на 9%; (4) память, загрузка, энергия, TTFT не измерены.

Sweep потоков при полном offload: CPU делает только embedding и сэмплинг, на 7B вышло 1,474–1,525 с (шум).

Настоящий материал: частичный offload g28 на 17% медленнее полного, g24 на 74–90%; при 0 слоёв на GPU 4→8 потоков дают 9,62→8,67 с (1,11×), упор в пропускную способность памяти. Гипотезу о том, какие слои уходят на CPU, проверить по логам.

## 4. Подсказка учителя про APEX (arXiv 2506.03296)
«Поймите, почему у них CPU+GPU быстрее, а у нас нет». APEX: throughput сервера с батчингом, VRAM под KV-кэш ограничивает батч, на CPU уходят attention и KV-кэш части запросов, CPU и GPU работают асинхронно; железо 2× Xeon, 180–250 ГБ RAM, T4/A10. У нас: latency одного запроса, всё в VRAM, на CPU целые слои, работа последовательная, GPU ждёт. CPU у APEX добавляет память, а не скорость. +84–96% к vLLM на T4, +11–22% на A10. Построен на открытом NEO; открыт ли код APEX, не проверено.

## 5. Новый вопрос
«При каких условиях CPU+GPU обгоняет GPU-only, и сдвигает ли язык запроса эту границу?» Гипотеза: у казахского в 3,2 раза больше токенов и KV-кэш, в VRAM меньше запросов, гибрид окупается раньше. RQ2: хватает ли политики, знающей длину последовательности.

## 6. План
Этап 1 (ноутбук Берика): телеметрия; подробный sweep по слоям и модель стоимости слоя; модель не в 8 ГБ (Qwen2.5-14B Q4); параллельные запросы EN+KK.
Этап 2 (AI lab): vLLM (GPU-only) + NEO (гибрид), параллельные EN/KK запросы, throughput и точка выигрыша гибрида, VRAM ограничить искусственно. Риск: настройка NEO.
Colab: только для отладки vLLM/NEO на T4, не для замеров.

## 7. Лаборатория (RTX 5090)
Одной карты хватит. Риски: при 32 ГБ дефицита памяти нет (ограничивать `gpu_memory_utilization`, батч или брать модель крупнее); 5090 слишком быстрая относительно CPU, гибрид может не выиграть (законный результат, предупредить учителя). Спросить: CPU, ядра, RAM, каналы памяти; машины со слабее GPU и сильным CPU; ОС; права на Docker/sudo; можно ли занять машину целиком.

## 8. Решение о нативном Linux
Снимает ловушки Windows/WSL: CUDA Sysmem Fallback, лимит RAM в WSL, шум и незакреплённые потоки. WSL-результаты с Linux-результатами напрямую не сравнивать.
